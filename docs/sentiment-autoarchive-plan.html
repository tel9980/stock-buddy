二、四条核心决策

决策 1 · 用「探测式触发」，不用固定时刻

最直觉的做法是定一个 crontab 式的「每交易日 15:30 跑一次」。我建议不这么做，改成轮询探测：

// 每 15 分钟一轮，全部条件满足才动手
1. 今天是周末？                    → 跳过（省掉 30% 的无效请求）
2. fetch_latest_trade_date() == 今天？→ 否则跳过（数据尚未落库）
3. 归档里已有今天？                  → 有则跳过（幂等）
4. 生成 → 渲染 → 落盘
维度固定时刻（15:30）探测式（推荐）
节假日元旦/春节/国庆休市无规律，需维护日历表数据没落库 → 自动跳过，不需要日历
服务当时没开直接错过，第二天也不会补下次启动自然补上
东财延迟落库15:30 跑可能拿到空数据数据落地了才跑
中途失败要自己写重试与退避下一轮天然重试，带退避
请求开销每天 1 次每天约 36 次探测，每次 1 个轻量请求

探测成本可以接受：fetch_latest_trade_date() 只取 1 行。实测今天 20:40 的返回值可作为判据验证——TRADE_DATE = 2026-09-02，行业清单 RPT_VALUEINDUSTRY_DET 返回 127 条，两个信号都指向「数据已定稿」。

决策 2 · scheduler 管「何时跑」，api 管「跑什么」

这是本轮最需要斟酌的架构问题。先看依赖现状：

appcore  ← 叶子
fetcher  → appcore
storage  → appcore
analyzer → appcore, fetcher, indicators   ← 注意：不依赖 storage
scheduler→ appcore, fetcher, storage      ← 注意：不依赖 analyzer / api
api      → 全部

而 build_daily 需要三样东西：Arc<EastmoneyFetcher>、storage::Database、以及渲染用的 sentiment_report::render —— 全都在 api 里。于是有三条路：

方案做法代价评价
A把 build_daily 下沉到 analyzer需给 analyzer 加 storage 依赖，分析层变存储感知分层变脏
B新建 crates/reports 承载编排分层最干净，但多一个 crate为一个功能建 crate，偏重
Cscheduler 只做引擎，任务体由 api 注入零依赖改动，零搬迁推荐
方案 C 的分工：scheduler 提供 tick 循环、交易日探测、任务注册与并发保护；api 在启动时注册一个闭包，闭包内部调用现成的 build_daily + render + 落盘。两者都待在各自已有的依赖边界内。

额外的好处是这个引擎是通用的：未来做T 提醒、自选股告警、行业轮动快照，都能挂到同一个 tick 上，符合你一贯的「通用化方案、避免逐页硬编码」。

决策 3 · 并发与失败

场景不处理会怎样对策
定时任务与用户手点撞车两次各 5,600 次抓取 → 必然触发限流进程内日期锁 Mutex<HashSet<String>>，同一日期只跑一个
上游限流返回残缺数据已有守卫，不落库沿用 is_degraded，下一轮自动重试
网络抖动可能白跑一轮不重试当次，等下一 tick（15 分钟后），天然退避

决策 4 · 补跑与留存

启动补跑：服务起来时回溯最近 N 个交易日（默认 3），把缺失的补上。这样长假回来不会留一屏空洞。必须串行 + 间隔，否则连续几天各 5,600 次抓取会直接把行情源打挂。

存储增长：需要提前看一眼，因为自动归档会让缓存表每天稳定增长。

当前库 3.4 MB / 5 个交易日，实测约 120 字节每行。年增 137 万行、约 160 MB 不算失控，但既然是无人值守的长跑进程，建议顺带加一条保留策略（只留最近 250 个交易日），避免一年后回来发现库涨到几百 MB。

三、实测数据（支撑上面的设计）

为确定调度器的时间预算，我实测了同一交易日（2026-09-02）走两条路径的成本：

路径耗时覆盖只数结果
快路径（东财官方口径）23.1 s5,188干净，无失败记录
慢路径（逐股聚合）109.8 s5,285340 只抓取失败（限流），且仍被判定完整而落库
缓存命中0.006 s—快三个数量级

快路径那 23 秒花在哪

环节耗时说明
全市场快表 RPT_DMSK_TS_STOCKNEW≈ 13 s瓶颈：5,196 条按 500/页串行翻 11 页，实测每页 1.0–1.4 s
板块快照 push2delay clist≈ 1 s2 页 + 80 ms 间隔
龙虎榜 / 题材 / 行业清单 / 指数≈ 9 s其中指数解析当天有告警
顺带发现一个真问题（建议同轮修）。今天 12:44 快路径第一步 fetch_board_snapshots 报 error decoding response body，导致整条快路径放弃、回落到 110 秒慢路径并触发 340 只限流。20:49 重试则正常——说明是间歇性故障。
排查已排除压缩问题：Cargo.lock 里没有 async-compression，reqwest 未启用 gzip，服务端对不声明编码的请求返回未压缩内容且无 Content-Encoding 头。更像连续翻页触发的连接重置。
对定时任务的杀伤在于：无人值守时偶发一次，就会变成「每晚 110 秒 + 限流 + 一份残缺日报被缓存」。建议在快照与快表请求上加一次重试（约 10 行改动），把 23 秒这条路径稳住。

四、实施步骤

1

scheduler 引擎

tick 循环 + 交易日探测 + 任务注册。纯时间逻辑，不碰业务。附单测：周末跳过、非交易日跳过、幂等跳过。

2

api 注入任务体

闭包内调用 build_daily → render → 写 data/reports/，让自动归档同时产出导出件（渲染仅 0.004 s，顺手把 has_export 点亮）。加进程内日期锁。

3

配置与可观测

环境变量开关（AUTO_ARCHIVE / 间隔 / 补跑天数）；job_runs 表记录每次运行；启动补跑串行执行。

4

前端接入

归档抽屉顶部显示「上次自动归档：09-02 15:32（23 秒，成功）」，失败时给出可见提示而不是只写日志。

可选同轮：给快路径的快照/快表请求加一次重试（见上节黄框）。

风险概率影响对策

六、验收标准

  • AUTO_ARCHIVE=off 时行为与现在完全一致（默认可关）
  • 开启后，服务在收盘后启动 → 15 分钟内自动补齐当日归档，且 has_export 为 true
  • 已有归档的日期重复触发 → 不再重新生成（日志可见「已存在，跳过」）
  • 周末 / 非交易日 → 不产生任何抓取请求
  • 删除某日归档后重启 → 补跑只补该日，不重复生成已有日期
  • 手动请求与定时任务同时触发 → 只有一份在跑
  • cargo test --workspace 全绿，含新增的调度逻辑单测
