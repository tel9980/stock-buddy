1. 问题：我们每换一天就白抓一次全市场

慢路径现在的取数逻辑有两处浪费叠在一起：

环节现状后果
bars_needed_for(date) 只取「够目标日用」的根数：ceil(自然日 × 5/7) + 15。
2026-08-27 只要 20 根，2026-06-30 要 62 根		 窗口刚好卡在目标日，多一天都不覆盖
load_or_fetch_bars 抓回来的整条序列里，只把目标日那一行落 daily_bar_cache 其余 19 / 61 根拿到手就丢掉

于是：看 8-27 花 13 秒抓 5,624 只；再点 6-30，同样的 5,624 只再抓一遍。而这两次抓的序列其实是高度重合的。

2. 关键实测：多取不要钱

这个方案成立的前提是「把窗口放宽不增加成本」。这需要验证，因为直觉上取 120 根应该比取 20 根慢。实测结果是不成立：

这里差点又踩一次「单样本当常态」。早先单独跑 6-30 拿到 21s，看上去像是「取 62 根比 20 根慢 65%」。 但改成交替顺序跑 3 轮后，两者中位数其实反过来（62 根还略快）。那个 21s 是当时上游正在限流， 不是 payload 的成本。（这是本会话第四次遇到同类问题：110s+340失败、并发 8 更快、腾讯 200 的幸运样本、这次的 21s。）

3. 方案：改两处

改动 1 · load_or_fetch_bars 把抓回来的整条序列落库，而不是只存目标日那一行。

改动 2 · 抓取窗口从「刚好够目标日」放宽到固定 SERIES_WINDOW_BARS = 120（约半年）。

不需要数据库迁移：daily_bar_cache 的主键本来就是 (stock_code, date)， 天然支持一只股票存多个日期。现有 prune_daily_bars(CACHE_KEEP_DATES = 250) 已经能按日期数封顶。

// 现状：只留目标日
let rows = fetched.iter().map(|b| (b.code, date, b.close, b.pct_change, b.amount));

// 改后：整条序列都留（伪代码）
for (klines, _status) in fetched_series {
    for k in klines {
        rows.push((code, k.date, k.close, k.pct_change, amount));
    }
}

4. 三个必须一起定的设计点

4.1 前复权会让缓存变陈旧 （这是真风险，不是理论问题）

腾讯是前复权：个股除权后，它历史上所有价格都会被重算。若我们缓存了前复权序列， 除权日一过，缓存里的历史价就全是错的，而且看不出来。新浪是不复权，没有这个问题。

麻烦在于：fetch_kline_with_status 返回 (Vec<Kline>, KlineStatus)， 没告诉我们这批数据来自哪个源——主源覆盖不到目标日时会静默回落到新浪。所以「只缓存不复权」需要先能识别来源。

选项做法优劣
A（推荐） 缓存整条序列，但给每只股票记一个 fetched_at，每天最多刷新一次。 新表 kline_series_meta(code, fetched_at)，约 3 行迁移。 前复权陈旧性被压到 1 天内；归档任务本来就每天跑，等于顺路复用。不限定来源，两个源都享受加速。
B 只缓存不复权（新浪）来源的序列；腾讯来源仍按现状只存目标日。 需要给返回值加来源标记。 无陈旧风险、无新表。
腾讯恢复后享受不到加速；且要改 trait 返回值。
C 不区分，全量缓存。 最简单，但除权季会静默产出错误的历史价格。不建议。

4.2 落库量一次性放大 120 倍

单只股票从落 1 行变成落 120 行。需要确认 save_daily_bars 是一次事务提交还是分批—— 67 万行一次性写要注意 SQLite 的 WAL 与事务开销。实施前先看这个函数的实现，必要时分批提交。

4.3 老数据的兼容

表里已有约 3.9 万行老缓存（7 个日期 × ~5,600）。它们没有 fetched_at 概念。 方案 A 下这些行会被当作「未刷新」而重抓一次——一次性成本，可接受，但要在验收里确认。

7. 回退

改动集中在 load_or_fetch_bars 一个函数和一处常量。回退方式：把 SERIES_WINDOW_BARS 改回 bars_needed_for(date)、只落目标日那一行即可，不需要回滚迁移（多出的列/表留着无害）。

5,624 → 9 次请求，17.6s → 1.4s。剩下那 9 次不是缺陷：它们是冷启动时真正抓取失败的股票（拿不到 K 线，因此没有序列记录），每次查询都会重试一次——这正是「自愈」的那条路径。

数据等价性：逐位一致

用旧代码（小窗口）产出的缓存当基准，清空后让新代码（120 根窗口）重抓，逐个数值对比：

2026-08-275,6240 行0 行0

窗口从 22 根放大到 120 根，没有改变任何一根 K 线的数值。原因：前复权的调整因子取决于「该日到最新日之间的分红」，与一次请求多少根无关；新浪本就是不复权。唯一例外是每串序列的首根——两家源都不返回它的涨跌幅（要靠前一根现算），落库会写成 0，将来查到那天会得到一个看起来正常、其实是假的数字，因此首根不落库。

落库成本

665,351 行写入 1,624 ms。这是把 save_daily_bars 从「逐行 INSERT」改成「每 100 行一条多行 INSERT」的结果；逐行版本在这个量级下要几十秒。库体积 5.6 MB → 约 60 MB，行数 38,965 → 670,636。

两处实施时才发现的问题

① 清理与序列记录会不一致。少数长期停牌股（实测 6 只）的「最近 120 根」会回溯到一年前，把缓存里的日期数从 ~120 推到 249，逼近 CACHE_KEEP_DATES = 250。一旦超过，清理会删掉最旧的日期，而序列记录仍声称覆盖它们——上层据此把「数据已被清理」误判成「当日停牌」，一个不报错、只会悄悄算错的错误。已在 prune_daily_bars 里同步失效这些记录（副本演练：清 49 行、失效 1 条记录，不变量校验 0 违反）。

②「每天最多刷新一次」其实没被触发。方案 A 设想靠每天重抓来压制前复权的陈旧性，但实现里有个提前返回：某日期的缓存若已齐全，missing 为空就直接返回，一只股票都不会重抓。于是序列只在「该股恰好缺这个日期」时才刷新，历史行的陈旧性并未被限制在 1 天内。当前全部数据走新浪（不复权），这个洞暂时不可见；但腾讯一旦恢复，除权季就会静默产出错误的历史价。

建议的补法（未实施，待确认）：在每天本就要跑的归档任务里，按 fetched_at 从旧到新滚动刷新一小片，例如 5633 / 7 ≈ 805 只/天。代价约 805 次请求（≈4s）+ 9.7 万行更新（≈0.3s），换来「7 天全量滚动一轮」的确定性上界。
